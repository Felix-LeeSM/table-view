# H4 진행 기준

H4 RDBMS intelligence 는 ERD/schema graph claim 과 검증 라우팅을 현재의 구현
상태에 맞추는 정합성 gate 다. Production ERD 는 schema-store cache 와
cached/fetched explicit index/constraint metadata 를 `SchemaGraph` input 으로
쓴다. Read-only dependency view, migration-impact summaries, and cached
read-only schema diff 는 이 shared graph/catalog path 를 재사용한다. Future
data compare 는 이 shared graph/catalog path 를 확장해야 하고, duplicate catalog
parsing 을 새로 만들지는 않는다.

| Gate | Current owner | H4 boundary |
|---|---|---|
| Schema metadata cache | `src/stores/schemaStore.ts`, `src/stores/schemaStore.tableMetadataCache.test.ts`, `src/stores/schemaStore.clearForConnection.test.ts` | schemas/tables/views/functions/postgresExtensions/tableColumnsCache/tableIndexesCache/tableConstraintsCache/triggers 가 current cache owner 의 범위다. |
| Production ERD graph input | `src/components/schema/SchemaErdPanel.tsx`, `src/lib/schemaGraphSnapshot.ts`, `src/components/schema/SchemaErdPanel.test.tsx`, `src/lib/schemaGraphSnapshot.test.ts` | Visible-table indexes/constraints are fetched when missing and passed into `SchemaGraph`; `ColumnInfo` PK/FK/CHECK metadata remains a synthetic fallback. |
| Reusable graph model | `src/lib/schemaGraph.ts`, `src/lib/schemaGraphRelationships.ts`, `src/components/schema/erdGraphModel.ts`, `src/components/schema/erdGraphModel.test.ts` | Graph extraction, relationship normalization, and the pure SchemaGraph -> canvas model (node sizing, elkjs layered options, search/selection helpers) are reusable beyond one visual panel. Placement itself is elkjs, not repo code. |
| Read-only dependency view | `src/components/schema/SchemaErdDependencyView.tsx`, `src/components/schema/SchemaErdCanvas.test.tsx`, `src/components/schema/SchemaErdPanel.test.tsx` | Selected ERD tables show incoming/outgoing FK tables/columns, related indexes/constraints, CHECK expressions, and visible metadata/SchemaGraph diagnostics without claiming FK row navigation. |
| Migration impact summaries | `src/lib/schemaGraphSelectors.ts`, `src/components/schema/SchemaGraphMigrationImpactSummary.tsx`, `src/hooks/useSchemaGraphIntelligence.ts`, `src/components/schema/DropTableDialog.tsx`, `src/components/schema/DropColumnDialog.tsx`, `src/components/structure/IndexesEditor.tsx`, `src/components/structure/ConstraintsEditor.tsx` | Table, column, constraint, and index removal previews show cached SchemaGraph impact summaries for dependent tables/columns/indexes/constraints/FKs and metadata diagnostics. This extends the existing DDL preview/confirm flow only; it does not change backend SQL generation/execution semantics. |
| Read-only schema diff | `src/lib/schemaGraphDiff.ts`, `src/components/schema/SchemaGraphDiffPanel.tsx`, `src/components/schema/SchemaErdPanel.tsx` | Cached same-source and cross-source RDBMS snapshots can be compared through SchemaGraph for table, column, index, constraint, and FK add/remove/change groups. | FK navigation boundary | `src/components/datagrid/DataGridTable.fk-navigation.test.tsx`, `docs/product/known-limitations.md` | Current FK row navigation is the DataGrid cell/icon path. ERD selection/search/node drag/canvas zoom/pan/fit/focus/highlight are local diagram interactions, not row navigation claims. |
| Future intelligence surfaces | `memory/engineering/architecture/data-source/memory.md`, this roadmap | Data compare surfaces must extend `SchemaGraph`/catalog input before product claim promotion. |
| Smoke/verification matrix | `docs/contributor-guide/testing-and-quality.md`, `e2e/smoke/erd-dense.spec.ts` | Dense ERD desktop/narrow screenshot smoke is wired for seeded PostgreSQL graph render, FK-direction layering, search, selection, node drag, and canvas zoom/fit evidence. It does not claim FK row navigation through ERD, schema diff, migration impact, or data compare. |

H4 umbrella closure means ERD/SchemaGraph support claims, reusable graph ownership,
cached read-only schema diff, dense ERD smoke, and smoke routing are aligned. It
does not mean data compare or migration/apply execution has shipped.

## ERD 캔버스 v1 MVP 경계 (2026-07-24 오너 grill)

ERD 캔버스 설계는 ADR 0054–0057 로 이미 잠겨 있다 (React Flow+elkjs 렌더러,
가상 FK polymorphic, layout persist/reconcile/undo, facet 필터). 아래 내용은 설계를
다시 논의하는 것이 아니라, v1 MVP 의 경계와 빌드 순서를 확정한 로드맵 스코핑이다.
React Flow+elkjs 캔버스 자체는 #1655 로 배송되었고 위의 gate 테이블이 그 상태를
가리키며, 남은 슬라이스는 아래 표에서 v1 과 v2, 후속으로 갈린다.

**v1 = 읽기전용 + 레이아웃 안정화.** layout persist 는 단순한 편집 기능이 아니라
elkjs 가 열람할 때마다 자동으로 재배치하는 동작이 세션 사이에서 안정적인가를 다루는
문제이므로 v1 에 포함한다. 가상 FK 편집은 v2 로 이월한다.

| Slice | 분류 | 추적 | 근거 |
|---|---|---|---|
| React Flow+elkjs 렌더러 | shipped | #1655, ADR 0054 | 가시 기능의 baseline 이다. 수제 렌더러를 일괄 교체하는 작업을 마쳤다. |
| semantic zoom 3단계 | shipped | #2149, ADR 0054 (2) | 고정 컬럼 상한을 폐기했다. elkjs 슬롯이 full-detail 높이 그대로여서 줌이 레이아웃을 다시 계산하지는 않지만, 그 대신 줌아웃을 해도 다이어그램이 촘촘해지지 않는다. 성능에 해당하는 나머지 절반은 아래 행이 맡는다. |
| FK 엣지 컬럼 앵커 + cardinality | shipped | #2151 | 엣지가 카드가 아니라 FK 컬럼 행에 붙고, 줌 단계가 그 행을 그리지 않으면 카드 가장자리로 물러난다. 표기는 한 행으로 고정된 끝의 개수만 세므로 어느 쪽이 1인지는 말하지 않고, 도착한 metadata 만 읽는다. 도착 상태별로 무엇이 나오는지는 `src/components/schema/erdGraphModel.test.ts` 의 `cardinality arrival states` 표가 고정한다. |
| facet 필터 | v1 | #1657, ADR 0057 | |
| schema diff 하이라이트 | shipped | #1662 | 카드 배지와 테이블 자신의 변경을 따르는 outline 을 쓴다. 캔버스는 현재 스키마로 그려지므로, 지워진 테이블은 카드가 없이 diff 패널의 행으로만 남는다. |
| layout persist/undo | v1 | #1660, ADR 0056 | 열람할 때마다 elkjs 가 재배치하는 동작의 세션 간 안정성을 닫는 것이 v1 의 목표다. |
| 가상 FK 렌더/추론/referential action | v2 | #1659 / #1668 / #1665, ADR 0055 | 편집 계열은 v2 로 이월한다. 렌더와 저장, reconcile 은 #1659 에서 갈라진 #2150 이 배송했고, 추론과 referential action 이 이 행에 남는다. |
| viewport 가상화 + worker 레이아웃 | 후속 | #1658 (성능 부분) | 실제 대형 스키마의 성능 pain 신호가 온 뒤에 승격한다. 지금은 수백 개 테이블 규모의 fixture 가 없다 (YAGNI). |
| 워크플로우 연결 | park | #1667 | 의도가 불명확하다. v1 범위 밖이며, 별도로 확인한 뒤에 다시 스코핑한다. |

**빌드 순서**: 가시 기능을 먼저 만든다. React Flow 기본 캔버스와 semantic zoom
위에 persist/facet/diff 를 먼저 얹는다. #1658 성능 작업(viewport 가상화와 worker
레이아웃)은 실제 대형 스키마의 성능 pain 신호가 온 뒤로 이월한다.

**a11y 내장 원칙**: #1663 (keyboard nav 와 color+shape 이중 인코딩)은 별도의 후기
게이트로 두지 않고 각 v1 기능에 내장한다.
