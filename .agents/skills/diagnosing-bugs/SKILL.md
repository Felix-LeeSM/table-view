# 버그 진단

원본: [mattpocock/skills `engineering/diagnosing-bugs`](https://github.com/mattpocock/skills/tree/main/skills/engineering/diagnosing-bugs).
피드백 루프 도구와 검증 명령을 이 저장소 것으로 바꿨다.

이 파일은 **원인을 찾는 절차**를 담는다. 원인을 찾은 뒤의 Red→Green→commit 순서는
`memory/workflow/bug-fix/memory.md` 가 정한다. 단계를 건너뛰려면 근거를 대라.

탐색 전에 읽을 것은 `memory/index/by-surface.md` 의 해당 surface 묶음과, 건드릴
영역의 ADR(`docs/decisions/`)이다.

## Phase 1: 피드백 루프를 만든다

**이 파일의 핵심이 전부 여기에 있다.** 나머지는 기계적이다. 이 버그에서 red 가
나는 **좁은 합격/불합격 신호**가 있으면 원인은 찾아지며, 이분법도 가설 검증도
계측도 그 신호를 소비할 뿐이다. 신호가 없으면 코드를 아무리 오래 들여다봐도
원인은 나오지 않는다.

여기에 불균형하게 시간을 써라. **공격적으로, 창의적으로, 포기하지 말고 만들어라.**

### 만드는 방법: 대략 이 순서로 시도한다

1. **실패하는 테스트를 쓴다.** 버그에 닿는 seam 이면 어느 층이든 괜찮고, 레이어
   선택 기준은 `memory/engineering/conventions/testing-scenarios/memory.md` P1 이
   정한다. 단일 파일은 `pnpm vitest run <path>` 또는
   `cd src-tauri && cargo test <name>` 로 돌린다.
   **Rust 는 `src-tauri` 에서 돌리는데**, 저장소 루트에는 manifest 가 없기
   때문이다. 이름이 어느 crate 에 있는지 모르면 `--workspace` 를 붙여 전부 훑고,
   좁힐 때 `-p` 로 고른다 (`db` · `models` · `storage` · `error` 는 core crate 다,
   #1769). `-p` 를 잘못 고르면 **cargo 는 0건을 돌리고 exit 0 으로 조용히
   끝나므로**, `running N tests` 의 N 을 보고 루프가 실제로 돌았는지 확인해라.
2. **실제 DB 를 띄워 fixture 루프를 돌린다.** `pnpm fixtures:start` (docker
   compose) 로 대상 DBMS 를 올리고 어댑터를 직접 호출한다. 드라이버 계층 버그의
   기본 경로다.
3. **파서 코어를 단독으로 호출한다.** `src-tauri/sql-parser-core` 와
   `mongosh-parser-core` 는 crate 단독으로 돌릴 수 있다. WASM 경계가 의심되면
   `pnpm build:sql-wasm` 이나 `pnpm build:mongosh-wasm` 으로 다시 만들어 양쪽을
   비교한다.
4. **differential 루프를 만든다.** 같은 입력을 두 경로에 넣고 출력을 diff 하는데,
   Rust 코어와 WASM, DBMS 두 종류, 옛 버전과 새 버전이 그 짝이 된다.
5. **캡처한 trace 를 재생한다.** 실제 쿼리와 응답, 이벤트 로그를 파일로 떠서 그
   코드 경로에 격리해 재생한다.
6. **e2e 스모크를 돌린다.** `pnpm build:e2e && pnpm test:e2e:smoke` (wdio) 로
   돌리며, 윈도우와 IPC 가 살아 있어야만 보이는 증상일 때만 쓴다. 느리고 결과가
   흔들리기 때문이다.
7. **버리는 harness 를 만든다.** 시스템의 최소 부분집합(어댑터 하나, 나머지는
   mock)을 띄워 함수 호출 하나로 버그 경로를 실행시킨다.
8. **property 나 fuzz 루프를 돌린다.** "가끔 결과가 틀리다" 면 임의 입력 1000개를
   돌려 실패 형태를 찾는다.
9. **이분법 harness 를 만든다.** 두 상태(커밋·데이터셋·버전) 사이에서 생겼으면
   "상태 X 로 부팅 → 검사 → 반복" 을 자동화해 `git bisect run` 에 입력한다.
10. **HITL bash 스크립트를 쓴다.** 최후 수단이다. 사람이 클릭해야만 하는
    상황이면 `.agents/skills/diagnosing-bugs/scripts/hitl-loop.template.sh` 로
    **사람에게 필요한 조작을 요구하면서** 루프를 구조화한다. 캡처된 출력이 다시
    입력이 된다.

루프를 제대로 만들면 버그는 90% 잡은 셈이다.

### 루프를 다듬는다

루프 자체를 하나의 산출물로 취급해라. 일단 루프가 하나 생기면 **다듬는다**:

- 더 빠르게 만들 수 있나? (셋업 캐시, 무관한 init 건너뛰기, 테스트 범위 좁히기)
- 신호를 더 정확하게 만들 수 있나? ("안 터졌다" 가 아니라 그 증상 자체를 단언한다)
- 더 결정론적으로 만들 수 있나? (`vi.useFakeTimers()`, `tokio::time::pause`,
  mockall `Sequence`, DB fixture 재생성을 쓰며, 원칙은 P5 가 정한다)

30초짜리 흔들리는 루프는 없는 것보다 조금 나을 뿐이고, 2초짜리 결정론적 루프는
디버깅 속도를 크게 끌어올린다.

### 비결정론적 버그

목표는 깨끗한 재현이 아니라 **재현율을 올리는 것**이다. 트리거를 100번 돌리고,
병렬로 걸고, 부하를 주고, 타이밍 창을 좁히고, sleep 을 주입한다. 50% flake 는
디버깅할 수 있고 1% 는 디버깅할 수 없으므로, 디버깅할 수 있을 때까지 재현율을
올려라.

### 정말 루프를 못 만들겠으면

멈추고 그렇게 말해라. 시도한 것을 나열하고 사용자에게 다음을 요청한다: (a) 재현되는
환경에 대한 접근, (b) 캡처된 산출물(쿼리 로그, DB 덤프, 타임스탬프 있는 화면 녹화),
(c) 임시 계측을 넣을 허가가 그것이다. **루프 없이 가설로 넘어가지 마라.**

### Phase 1 완료 조건: red 가 나는 좁은 루프

**명령 하나**를 댈 수 있어야 한다. 이미 최소 한 번 돌려서 그 호출과 출력을
붙일 수 있어야 하고, 다음 넷을 만족해야 한다.

- [ ] **red 가 난다.** 실제 버그 코드 경로를 실행시키고 **사용자가 말한 그 증상**을
      단언한다. "에러 없이 돈다" 가 아니라 이 버그를 잡을 수 있어야 한다.
- [ ] **결정론적이다.** 매번 같은 판정을 낸다. (비결정론 버그라면 위에서 말한
      높은 재현율로 고정한다.)
- [ ] **빠르다.** 분 단위가 아니라 초 단위로 끝난다.
- [ ] **agent 가 돌릴 수 있다.** 사람 없이 실행되며, 사람이 필요하면 HITL
      스크립트로만 돌린다.

이 명령이 있기 전에 코드를 읽어 이론을 세우고 있다면 **멈춰라. 가설로 직행하는
것이 이 파일이 막으려는 바로 그 실패다.** red 나는 명령이 없으면 Phase 2 도 없다.

## Phase 2: 재현하고 최소화한다

루프를 돌려 red 를 본다. 다음을 확인한다:

- [ ] 루프가 내는 실패가 **사용자가 말한** 그 실패이며, 근처의 다른 실패가 아니다.
      다른 버그를 잡으면 다른 fix 가 나온다.
- [ ] 여러 번 돌려도 재현된다.
- [ ] 정확한 증상(에러 메시지, 틀린 출력, 걸린 시간)을 캡처해 두었다. 나중 단계에서
      fix 가 그 증상을 실제로 없앴는지 확인할 근거가 되기 때문이다.

### 최소화

red 가 나면 **여전히 red 인 가장 작은 시나리오**로 줄인다. 입력과 호출자, 설정,
데이터, 단계를 **하나씩** 빼고 매번 다시 돌린다. 그러면 실패를 지탱하는 요소만
남는다.

이렇게 하는 이유는 최소 재현이 Phase 3 의 가설 공간을 줄이고 Phase 5 의 회귀
테스트가 되기 때문이다.

완료 조건은 **남은 요소 전부가 실패를 지탱하는 상태**, 즉 아무거나 하나 빼면
green 이 되는 상태다.

## Phase 3: 가설을 세운다

**3~5개를 순위 매겨** 먼저 만든다. 하나만 세우면 처음 떠오른 그럴듯한 생각에
판단이 고정된다.

각 가설은 **반증 가능**해야 한다. 그 가설이 내는 예측을 적어라.

> 형식: "X 가 원인이면, Y 를 바꾸면 버그가 사라진다 / Z 를 바꾸면 심해진다."

예측을 적지 못하면 그것은 가설이 아니라 직관이므로, 버리거나 예측을 적을 수 있을
만큼 구체화해라.

**순위 목록을 사용자에게 먼저 보여라.** 도메인 지식으로 순위가 즉시 바뀌는 일이
잦다("3번 쪽을 방금 배포했다"). 비용이 적은 체크포인트다. 다만 답을 기다리며 멈춰
있지는 마라. 사용자가 없으면 내가 매긴 순위대로 진행한다.

## Phase 4: 계측한다

각 프로브는 Phase 3 의 특정 예측에 대응해야 한다. **한 번에 변수 하나만 바꾼다.**

도구는 다음 순서로 고른다:

1. 디버거나 REPL 검사가 가능하면 그것을 쓴다. breakpoint 하나가 로그 열 줄보다
   낫다.
2. 가설을 가르는 경계에 **표적 로그**를 넣는다.
3. "다 찍고 grep" 은 절대 하지 않는다.

**디버그 로그마다 고유 접두사를 붙인다.** 예를 들면 `[DEBUG-a4f2]` 처럼 붙인다.
그러면 마지막 청소가 grep 한 번으로 끝난다. 태그가 없는 로그는 지우지 못하고 남는다.

**성능 갈래는 다르다.** 성능 회귀에서는 로그가 대개 맞지 않는 도구다. 대신 기준선을
먼저 재고(타이밍 harness, `performance.now()`, 프로파일러, 쿼리 플랜) 이분법으로
좁힌다. 재는 것이 먼저이고 고치는 것이 나중이다.

## Phase 5: fix 와 회귀 테스트

회귀 테스트를 fix **전에** 쓰되, **올바른 seam** 이 있을 때만 그렇게 한다.

올바른 seam 은 테스트가 **호출 지점에서 일어나는 실제 버그 패턴**을 그대로
실행시키는 자리다. 남은 seam 이 너무 얕으면(버그가 호출자 여럿을 필요로 하는데
단일 호출자 테스트밖에 없는 경우, 버그를 부른 연쇄를 재현하지 못하는 단위 테스트)
거기 놓인 회귀 테스트는 거짓 안심을 준다. 층 선택 기준은 P1 이 정한다.

**올바른 seam 이 없다면 그 자체가 발견이므로 기록해라.** 구조가 이 버그를 잠그지
못하게 막고 있다는 뜻이며, 그 발견은 Phase 6 으로 넘긴다.

seam 이 있다면 최소 재현을 그 seam 의 실패 테스트로 바꾸고 → 실패를 확인하고 →
fix 하고 → 통과를 확인한 뒤 → Phase 1 루프를 **최소화 전 원본 시나리오**로 다시
돌린다.

여기서부터는 `memory/workflow/bug-fix/memory.md` 의 순서를 따른다.

## Phase 6: 청소와 사후 점검

완료를 선언하기 전에 다음을 반드시 확인한다:

- [ ] 원래 재현이 더 이상 재현되지 않는다 (Phase 1 루프를 다시 돌려 확인한다)
- [ ] 회귀 테스트가 통과한다 (또는 seam 이 없다는 사실을 기록했다)
- [ ] `[DEBUG-...]` 계측을 전부 제거했다 (`git grep 'DEBUG-'` 로 확인한다)
- [ ] 버리는 harness 를 지웠다
- [ ] 맞은 것으로 판명된 가설을 커밋이나 PR 메시지에 적었다 (다음 사람이 그것을
      읽고 배운다)
- [ ] fixture 를 띄웠으면 `pnpm fixtures:stop` 으로 내렸다

**그리고 「무엇이 이 버그를 막을 수 있었을까」를 묻는다.** 답이 구조 변경이면(테스트
seam 이 없다, 호출자가 뒤엉켰다, 결합이 숨어 있다)
`memory/engineering/conventions/refactoring/memory.md` 로 넘긴다. 이 권고는 fix 가
들어간 **뒤에** 하는데, 시작할 때보다 지금 아는 것이 많기 때문이다.
