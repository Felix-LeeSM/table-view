# 버그 진단

원본: [mattpocock/skills `engineering/diagnosing-bugs`](https://github.com/mattpocock/skills/tree/main/skills/engineering/diagnosing-bugs).
피드백 루프 도구와 검증 명령을 이 저장소 것으로 바꿨다.

이 방은 **원인을 찾는 절차**다. 원인을 찾은 뒤의 Red→Green→commit 순서는
`memory/workflow/bug-fix/memory.md` 가 SOT 다. 단계를 건너뛰려면 근거를 대라.

탐색 전에 읽을 것: `memory/index/by-surface.md` 의 해당 surface 묶음,
건드릴 영역의 ADR (`docs/decisions/`).

## Phase 1 — 피드백 루프를 만든다

**이 방의 전부가 여기다.** 나머지는 기계적이다. 이 버그에서 red 가 나는 **좁은
합격/불합격 신호**가 있으면 원인은 찾아진다 — 이분법도 가설 검증도 계측도 그
신호를 소비할 뿐이다. 신호가 없으면 코드를 아무리 노려봐도 안 나온다.

여기에 불균형하게 시간을 써라. **공격적으로, 창의적으로, 포기하지 말고.**

### 만드는 방법 — 대략 이 순서로

1. **실패하는 테스트.** 버그에 닿는 seam 이면 어느 층이든 — 레이어 선택 기준은
   `memory/engineering/conventions/testing-scenarios/memory.md` P1.
   단일 파일: `pnpm vitest run <path>` / `cargo test --manifest-path src-tauri/Cargo.toml <name>`
2. **실제 DB 를 띄운 fixture 루프.** `pnpm fixtures:start` (docker compose) 로
   대상 DBMS 를 올리고 어댑터를 직접 호출한다. 드라이버 계층 버그의 기본 경로다.
3. **파서 코어 단독 호출.** `src-tauri/sql-parser-core` / `mongosh-parser-core` 는
   crate 단독으로 돌릴 수 있다. WASM 경계가 의심되면 `pnpm build:sql-wasm` /
   `pnpm build:mongosh-wasm` 로 다시 만들어 양쪽을 비교한다.
4. **differential 루프.** 같은 입력을 두 경로에 넣고 출력을 diff 한다 — Rust 코어
   대 WASM, DBMS 두 종류, 옛 버전 대 새 버전.
5. **캡처한 trace 재생.** 실제 쿼리/응답/이벤트 로그를 파일로 떠서 그 코드 경로에
   격리 재생한다.
6. **e2e 스모크.** `pnpm build:e2e && pnpm test:e2e:smoke` (wdio). 윈도우와 IPC 가
   살아 있어야만 보이는 증상일 때만 — 느리고 흔들린다.
7. **버리는 harness.** 시스템의 최소 부분집합(어댑터 하나, 나머지는 mock)을 띄워
   함수 호출 하나로 버그 경로를 때린다.
8. **property / fuzz 루프.** "가끔 결과가 틀리다" 면 임의 입력 1000개를 돌려
   실패 모양을 찾는다.
9. **이분법 harness.** 두 상태(커밋·데이터셋·버전) 사이에서 생겼으면 "상태 X 로
   부팅 → 검사 → 반복" 을 자동화해 `git bisect run` 에 먹인다.
10. **HITL bash 스크립트.** 최후 수단. 사람이 클릭해야만 하면
    `.agents/skills/diagnosing-bugs/scripts/hitl-loop.template.sh` 로 **사람을
    몰아서** 루프를 구조화한다. 캡처된 출력이 다시 입력이 된다.

루프를 제대로 만들면 버그는 90% 잡힌 것이다.

### 루프를 조인다

루프 자체를 제품으로 다뤄라. 일단 하나 생기면 **조인다**:

- 더 빠르게? (셋업 캐시, 무관한 init 건너뛰기, 테스트 범위 좁히기)
- 신호를 더 날카롭게? ("안 터졌다" 가 아니라 그 증상 자체를 단언)
- 더 결정론적으로? — `vi.useFakeTimers()`, `tokio::time::pause`, mockall
  `Sequence`, DB fixture 재생성. 원칙은 P5.

30초짜리 흔들리는 루프는 없는 것보다 조금 나을 뿐이고, 2초짜리 결정론적 루프는
디버깅 초능력이다.

### 비결정론적 버그

목표는 깨끗한 재현이 아니라 **재현율을 올리는 것**이다. 트리거를 100번 돌리고,
병렬로 걸고, 부하를 주고, 타이밍 창을 좁히고, sleep 을 주입한다. 50% flake 는
디버깅 가능하고 1% 는 불가능하다 — 가능해질 때까지 올려라.

### 정말 루프를 못 만들겠으면

멈추고 그렇게 말해라. 시도한 것을 나열하고 사용자에게 요청한다 — (a) 재현되는
환경 접근, (b) 캡처된 산출물(쿼리 로그, DB 덤프, 타임스탬프 있는 화면 녹화),
(c) 임시 계측을 넣을 허가. **루프 없이 가설로 넘어가지 마라.**

### Phase 1 완료 조건 — red 가 나는 좁은 루프

**명령 하나**를 댈 수 있어야 한다. 이미 최소 한 번 돌려서 그 호출과 출력을
붙일 수 있고, 다음 넷을 만족해야 한다.

- [ ] **red 가 난다** — 실제 버그 코드 경로를 몰고 **사용자가 말한 그 증상**을
      단언한다. "에러 없이 돈다" 가 아니라 이 버그를 잡을 수 있어야 한다.
- [ ] **결정론적** — 매번 같은 판정. (비결정론 버그는 위의 고정된 높은 재현율)
- [ ] **빠르다** — 분이 아니라 초.
- [ ] **agent 가 돌릴 수 있다** — 무인 실행. 사람이 필요하면 HITL 스크립트로만.

이 명령이 있기 전에 코드를 읽어 이론을 세우고 있다면 **멈춰라 — 가설로 직행하는
것이 이 방이 막는 바로 그 실패다.** red 나는 명령이 없으면 Phase 2 는 없다.

## Phase 2 — 재현하고 최소화한다

루프를 돌려 red 를 본다. 확인할 것:

- [ ] 루프가 내는 실패가 **사용자가 말한** 그 실패다 — 근처의 다른 실패가 아니다.
      다른 버그를 잡으면 다른 fix 가 나온다.
- [ ] 여러 번 돌려도 재현된다.
- [ ] 정확한 증상(에러 메시지, 틀린 출력, 걸린 시간)을 캡처해 뒀다 — 나중 단계가
      fix 가 그 증상을 실제로 없앴는지 확인할 근거다.

### 최소화

red 가 나면 **여전히 red 인 가장 작은 시나리오**로 줄인다. 입력·호출자·설정·
데이터·단계를 **하나씩** 빼고 매번 다시 돌린다. 남는 것은 실패를 지탱하는 것뿐.

이유: 최소 재현은 Phase 3 의 가설 공간을 줄이고, Phase 5 의 회귀 테스트가 된다.

**남은 요소 전부가 지탱한다** — 아무거나 하나 빼면 green 이 된다 — 가 완료 조건.

## Phase 3 — 가설을 세운다

**3~5개를 순위 매겨** 먼저 만든다. 하나만 세우면 첫 그럴듯한 생각에 닻이 내린다.

각 가설은 **반증 가능**해야 한다. 그 가설이 내는 예측을 적어라.

> 형식: "X 가 원인이면, Y 를 바꾸면 버그가 사라진다 / Z 를 바꾸면 심해진다."

예측을 못 적으면 그건 감이다 — 버리거나 날카롭게 하라.

**순위 목록을 사용자에게 먼저 보여라.** 도메인 지식으로 순위가 즉시 바뀌는 일이
잦다("3번 쪽을 방금 배포했다"). 값싼 체크포인트다. 다만 붙잡고 기다리지는 마라 —
사용자가 없으면 내 순위대로 간다.

## Phase 4 — 계측한다

각 프로브는 Phase 3 의 특정 예측에 대응해야 한다. **한 번에 변수 하나만.**

도구 우선순위:

1. 디버거 / REPL 검사가 가능하면 그것. breakpoint 하나가 로그 열 줄을 이긴다.
2. 가설을 가르는 경계에 **표적 로그**.
3. "다 찍고 grep" 은 절대 하지 않는다.

**디버그 로그마다 고유 접두사를 붙인다** — 예: `[DEBUG-a4f2]`. 마지막 청소가
grep 한 번이 된다. 태그 없는 로그는 살아남는다.

**성능 갈래.** 성능 회귀에서는 로그가 대개 틀린 도구다. 대신 기준선을 먼저 재고
(타이밍 harness, `performance.now()`, 프로파일러, 쿼리 플랜) 이분법으로 좁힌다.
재는 게 먼저, 고치는 게 나중이다.

## Phase 5 — fix + 회귀 테스트

회귀 테스트를 fix **전에** 쓴다 — 단 **올바른 seam** 이 있을 때만.

올바른 seam 은 테스트가 **호출 지점에서 일어나는 실제 버그 패턴**을 그대로
운동시키는 자리다. 남은 seam 이 너무 얕으면(버그가 호출자 여럿을 필요로 하는데
단일 호출자 테스트밖에 없는 경우, 버그를 부른 연쇄를 재현 못 하는 단위 테스트)
거기 놓인 회귀 테스트는 거짓 안심을 준다. 층 선택은 P1.

**올바른 seam 이 없다면 그 자체가 발견이다.** 적어라. 구조가 이 버그를 잠그지
못하게 막고 있는 것이다. Phase 6 으로 넘긴다.

있다면: 최소 재현을 그 seam 의 실패 테스트로 바꾸고 → 실패를 보고 → fix 하고 →
통과를 보고 → Phase 1 루프를 **최소화 전 원본 시나리오**로 다시 돌린다.

여기서부터는 `memory/workflow/bug-fix/memory.md` 의 순서를 따른다.

## Phase 6 — 청소 + 사후

완료 선언 전에 필수:

- [ ] 원래 재현이 더 이상 재현되지 않는다 (Phase 1 루프 재실행)
- [ ] 회귀 테스트가 통과한다 (또는 seam 부재를 기록했다)
- [ ] `[DEBUG-...]` 계측을 전부 제거했다 (`git grep 'DEBUG-'` 로 확인)
- [ ] 버리는 harness 를 지웠다
- [ ] 맞은 것으로 판명된 가설을 커밋/PR 메시지에 적었다 — 다음 사람이 배운다
- [ ] fixture 를 띄웠으면 `pnpm fixtures:stop`

**그리고 묻는다: 무엇이 이 버그를 막았을까?** 답이 구조 변경이면(테스트 seam 이
없다, 호출자가 엉켰다, 결합이 숨어 있다) `memory/engineering/conventions/refactoring/memory.md`
로 넘긴다. 이 권고는 fix 가 들어간 **뒤에** 한다 — 시작할 때보다 지금 아는 게
많다.
